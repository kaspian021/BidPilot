# معماری BidPilot

هدف: یک هسته‌ی پایدار که «منبع پروژه» و «مقصد اطلاع‌رسانی» قابل تعویض باشند، بدون بازنویسی منطق کسب‌وکار.

## لایه‌ها

```
            ┌────────────────────────────────────────────────────────────┐
            │                         CLI / Scheduler                    │
            │              (once · run · preview · demo · doctor)        │
            └───────────────────────────┬────────────────────────────────┘
                                        │
                        ┌───────────────▼───────────────┐
                        │          Application          │  wiring + lifecycle
                        │  config · db · sources · …    │
                        └───────────────┬───────────────┘
                                        │
   ┌────────────┐   ┌────────────┐  ┌───▼─────────┐  ┌──────────────┐  ┌────────────┐
   │  Sources   │──▶│  Filters   │─▶│  Pipeline   │─▶│   Pricing    │─▶│  Proposals │
   │ (adapters) │   │  (rules)   │  │ (orchestr.) │  │ (strategies) │  │ LLM+template│
   └────────────┘   └────────────┘  └───┬─────┬───┘  └──────────────┘  └────────────┘
                                        │     │
                        ┌───────────────▼─┐ ┌─▼──────────────┐
                        │  RateLimiter    │ │  Notifications │
                        │ (caps, spacing) │ │ (Telegram/... )│
                        └───────────────┬─┘ └────────────────┘
                                        │
                             ┌──────────▼──────────┐
                             │ Repository (SQLAlch)│
                             │  SQLite / Postgres  │
                             └─────────────────────┘
```

## قراردادهای کلیدی

| مفهوم | قرارداد |
|---|---|
| `Project` | هر پروژه از هر سایتی به یک ساختار نرمال تبدیل می‌شود (`source`, `external_id`, `title`, `description`, `budget`, …). `uid = source:external_id` |
| `Budget` | همیشه در **تومان** و عدد صحیح؛ بازه + متن اصلی برای شفافیت |
| `PricingStrategy` | یک متد: `price(project, budget) -> PricingResult \| None` |
| `Source` | دو متد اجباری: `fetch_projects()` و `submit_bid(...)`؛ هیچ استثنای «انتظاری» نباید بالا برود، باید `SubmissionResult` برگردد |
| `Notifier` | `send(event) -> bool`؛ خطای یک کانال بقیه را متوقف نمی‌کند |
| `Event` | هر اتفاق قابل اطلاع: پروژه جدید، ارسال، رد، خطا، گزارش |

## چرا این تقسیم‌بندی مهم است؟

1. **تعویض‌پذیری**: افزودن سایت دوم فقط یک آداپتور است؛ قیمت‌گذاری، اعتبارسنجی متن، ضدتکرار و تلگرام مشترک می‌مانند.
2. **قابل تست بودن**: هر لایه با mock مستقل تست می‌شود (بدون تماس با سایت واقعی).
3. **قابل توضیح بودن**: هر تصمیم (`skip`، قیمت، منبع متن) در دیتابیس و لاگ ثبت می‌شود؛ می‌توانید بپرسید «چرا این پروژه رد شد؟» و جواب بگیرید.
4. **مقاوم بودن**: خطا در یک پروژه، دسته را متوقف نمی‌کند؛ خطا در یک دوره، daemon را نمی‌کشد (backoff نمایی دارد).

## جریان یک پروژه در `Pipeline.process_project`

1. **Dedupe** — آیا `(source, external_id)` قبلاً دیده شده؟ (unique index در DB)
2. **Persist** — پروژه ذخیره می‌شود (حتی اگر رد شود؛ برای تحلیل بعدی).
3. **Filter** — کلیدواژه‌های ممنوع/موردعلاقه، دسته، حداقل/حداکثر بودجه.
4. **Notify (new)** — پیام «پروژه جدید» به تلگرام.
5. **Pricing** — استراتژی فعال؛ قیمت همیشه clamp داخل بازه‌ی کارفرما.
6. **Proposal** — LLM (با fallback) یا قالب؛ سپس اعتبارسنجی و در صورت نیاز «تعمیر».
7. **Rate limit** — سقف ساعتی/روزانه و فاصله‌ی حداقلی از DB خوانده می‌شود (پس با ری‌استارت هم درست است).
8. **Submit / Dry-run** — ارسال واقعی یا شبیه‌سازی.
9. **Record + Notify** — نتیجه در `bids` ذخیره و در تلگرام گزارش می‌شود.

هر مرحله fail-safe است: خطا → `bids.status = failed/skipped` + پیام تلگرام، و ادامه‌ی دسته.

## مقیاس‌پذیری

- **عمودی**: تا صدها پروژه در دقیقه با یک process کافی است (گلوگاه واقعی، محدودیت خود سایت است).
- **افقی**: نفسِ کار را می‌توان به چند worker تقسیم کرد؛ چون dedupe و rate-limit روی دیتابیس مشترک‌اند (Postgres). `SELECT … FOR UPDATE`/unique constraint از پیشنهاد تکراری جلوگیری می‌کند.
- **تفکیک منابع**: `bidpilot run --source parscoders` روی یک worker و source دیگر روی worker دوم.
- **قیمت‌گذاری/متن**: LLM را می‌توان به یک سرویس داخلی یا صف (Celery/RQ) منتقل کرد؛ نقطه‌ی اتصال `ProposalGenerator` است.

## ایده‌های توسعه‌ی آینده

- `Sink` برای تحلیل (ClickHouse/Postgres جداجدا) و داشبورد برد/باخت.
- استراتژی قیمت یادگیرنده (multi-armed bandit بر اساس نرخ پاسخ).
- پشتیبانی از WebSocket/SSE اگر سایت منبع بدهد (سریع‌تر از polling).
- صف تلگرام با retry (اگر API قطع بود، پیام گم نشود).
